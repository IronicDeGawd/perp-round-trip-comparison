DreamDEX vs Hyperliquid
View code on GitHub
15 October 2026. Testnets, timed from a server in AWS Tokyo next to both venues.

Opening and closing a perp: one transaction against two orders

I had a bot open and close the same BTC position on DreamDEX and on Hyperliquid, timed to on-chain settlement. DreamDEX did both legs in one transaction.

Verdict. DreamDEX settles the whole round trip in 279 ms because it is one transaction: the open and the close are matched inside the same on-chain call and finish in the same block. Hyperliquid needs two orders that settle one after the other, so it pays for settlement twice: 1.41 s.
Three real runs at real speed. Each Start press runs the same open-and-close on both venues at the same moment; each row fills when its chain settles.

Why it is faster

The gap is not a faster server or a better connection: both bots ran from the same machine. It comes from how many times each venue has to settle before the trade is done.

Hyperliquid

It has to wait for the open before it can close

The close is a reduce-only order: it can only shrink a position that already exists. So the bot sends the open, waits for HyperCore to settle it, and only then sends the close, which settles again. Two consensus rounds, back to back.

src/hyperliquid.mjstwo orders, one after the other
// leg 1: open. Returns once HyperCore has settled the fill (~700 ms)
const o = await exch.order({ orders: [
  { a: btc, b: true,  p: buyPx,  s: size, r: false, t: { limit: { tif: "Ioc" } } },
] });

// leg 2: close. Reduce-only, so it cannot start until leg 1 exists (~700 ms more)
const c = await exch.order({ orders: [
  { a: btc, b: false, p: sellPx, s: size, r: true,  t: { limit: { tif: "Ioc" } } },
] });
DreamDEX

It sends both legs in one transaction

The wallet is delegated through EIP-7702 to a small batcher contract. The bot sends one transaction to itself that calls execute([open, close]), and the batcher places the buy, then the sell, against the pool in the same call.

src/dreamdex.mjsone transaction, both legs
// both orders go into one batch
const calls = [
  { to: btcPerp, value: 0n, data: encode("placeOrder", orderArgs(true,  buy))  },  // open
  { to: btcPerp, value: 0n, data: encode("placeOrder", orderArgs(false, sell)) },  // close
];

// one transaction to our own (7702-delegated) address runs the batch
const hash = await wallet.sendTransaction({ to: me, data: encode("execute", [calls]) });
await pub.waitForTransactionReceipt({ hash });   // one inclusion = open and close settled
DreamDEX

The order book is a contract, so matching happens inside the transaction

On DreamDEX the order book lives on chain. When the transaction executes, the buy matches and the position opens, then the sell matches and the position closes, all in one execution. There is no separate matching engine to wait for and no second message. When the block includes the transaction, the trade is finished.

Somnia

The chain includes the transaction quickly

With one transaction, the only wait left is for Somnia to put it in a block. From Tokyo the node accepted it in about 15 ms, and it settled in 279 ms on this run. In earlier testing it sometimes landed in the same block it was sent in, in 33 ms.

“Couldn't Hyperliquid just batch them?”

Its API can put several orders in one signed action, but a reduce-only close still needs the open to have filled, and there is no on-chain call that opens and closes as one all-or-nothing unit. A smart contract that wants to trade on HyperCore goes through CoreWriter, which settles asynchronously. A faster bot does not remove the second settlement; only doing both legs in one transaction does.

Read before you quote these numbers
Atomicity, not gas
The EIP-7702 authorization costs about 1.57M gas on Somnia, so batching saves nothing on fees. The gain is one all-or-nothing transaction you sign yourself.
Hyperliquid's time is real
A read from the same server took ~9 ms, so ~700 ms per order is HyperCore consensus, not network lag.
Location matters
From a laptop the same DreamDEX round trip read ~1.4 s. Measure next to the venues or expect inflated numbers.

Method and reproduce
